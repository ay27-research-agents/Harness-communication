# Communication security visibility

Each delivered direct message in an agent's `directInbox` now includes a
`communicationSecurity` object generated by the harness from the delivery receipt.
It is included in the model's ordinary CONTEXT JSON. No trust instructions, trust
scores, or recommendations were added.

Current local socket messages show transport `local-tcp`, encryption `none`,
certificateVerification `not-used`, and messageSignature `not-present`.
Inline deliveries show `in-process` and encryption `not-applicable`.
Missing or unrecognized transport information shows `unknown` rather than
claiming verification. Message content cannot overwrite these fields.

This describes the delivery connection, not storage encryption or factual accuracy.
It does not create cryptographic signatures. The staged TLS transport is not yet
integrated into this local runtime; a future TLS delivery must supply verified
receiver-side connection evidence before any encrypted/verified label is emitted.
Subject posts currently retain their existing format; they are shared-store entries,
not direct peer deliveries.

Restart the harness and start a fresh run to see the fields on newly processed
messages. Existing completed model turns are not rewritten. Labels are currently
always visible; a hidden-label experimental condition is not yet implemented.
